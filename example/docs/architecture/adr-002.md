## Context

As part of the AWS-to-self-hosted migration (OPP-002), we need a container orchestration platform for our bare-metal servers. On AWS we relied on ECS with Fargate, which handled scheduling, networking, and auto-scaling transparently. Moving to self-hosted infrastructure requires us to choose an orchestration solution that can run on bare-metal without cloud provider integration.

We evaluated Kubernetes (k3s), Docker Swarm, and Nomad. The team has existing Kubernetes experience from managing staging environments, and the ecosystem tooling (Helm, ArgoCD, Prometheus) is mature.

## Decision

We will use k3s (lightweight Kubernetes) on bare-metal servers. k3s was chosen over full Kubernetes because it bundles all control plane components into a single binary, reducing operational complexity on bare-metal where we manage our own etcd and load balancers.

The cluster runs 3 control plane nodes for HA and N worker nodes. MetalLB provides load balancer services without a cloud provider, and Longhorn handles distributed block storage for stateful workloads. Ingress is handled by Traefik (bundled with k3s).

## Consequences

### Positive

- k3s is production-ready Kubernetes with a smaller footprint — single binary, embedded SQLite/etcd, minimal memory overhead.
- Existing Helm charts and ArgoCD pipelines from staging transfer directly to the new cluster.
- MetalLB + Traefik give us full ingress and load balancing without cloud provider dependencies.
- Longhorn provides replicated storage across nodes, eliminating the need for a SAN or NFS.

### Negative

- Bare-metal Kubernetes lacks cloud auto-scaling — capacity planning must be done manually with headroom.
- Hardware failures require manual intervention (swap disks, reseat memory) unlike cloud instances that self-heal.
- k3s bundles components (Traefik, CoreDNS) that may need to be replaced as requirements grow, adding migration effort later.
