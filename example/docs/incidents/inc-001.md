## Summary

On 2025-03-15, the production API began returning 503 errors at a rate of ~40% of all requests. The root cause was exhaustion of the PgBouncer connection pool. A long-running analytics query held 60 connections for over 45 minutes, starving the application of available database connections. The issue affected all API endpoints that require database access. Approximately 12,000 requests failed over the 2-hour incident window before mitigation.

## Root Cause

The analytics team ran a batch query that opened 60 parallel connections through PgBouncer's transaction pooling mode. PgBouncer was configured with a global pool of 100 connections and no per-user or per-database limits. The analytics query consumed 60% of the total pool, leaving only 40 connections for all production API traffic. Under normal load the API requires 50-70 connections, so the remaining 40 were insufficient and new requests queued until the PgBouncer wait timeout (30s) expired, resulting in 503 responses.

## Five Whys

1. Why did the API return 503 errors?
└► Because PgBouncer had no available connections to assign to incoming requests.

2. Why were there no available connections?
└► Because a single analytics query was holding 60 of the 100 available connections.

3. Why could a single query take 60 connections?
└► Because PgBouncer had no per-user or per-role connection limits configured.

4. Why were there no per-user limits?
└► Because the initial PgBouncer setup (part of ADR-001) used default configuration without production-hardening.

5. Why was the analytics query running against the primary?
└► Because there is no read replica configured for analytics workloads yet.
